# Supported inputs and limits

This page describes the 1.0 command set. The [Releases page](https://github.com/Pastalikek65/archivebridge/releases) lists which package versions and platforms are available, their checksums, and version-specific verification scope. Windows x64 and Linux x64 are the supported package targets; check the matching release entry for its actual files and evidence. Downloaded packages need no Go, Python, or Node installation. Packages are unsigned. Source builds do not inherit release evidence. The local viewer is intended for a current Chromium-based browser.

## Takeout inputs

Source parts may be ZIP, `.tar.gz`, or `.tgz`. Supported media extensions include common JPEG, PNG, GIF, WebP, HEIC, TIFF, AVIF, and camera-raw images, along with MP4, MOV, MKV, WebM, AVI, and other documented video extensions. ArchiveBridge preserves bytes; it does not decode or convert media. The viewer previews JPEG and PNG only. Other supported media can be downloaded. Preview headers are limited to 1 MiB, dimensions to 32,768 pixels per side, and total pixels to 64 million. A rejected preview does not alter the stored original.

Default core limits are 16 parts, 100,000 entries across all parts including directories, 32 GiB per supported media member, and 1 TiB of expanded regular-member payload. Each ZIP central directory is limited to 64 MiB, each member name to 1,024 UTF-8 bytes, and combined member paths to 16 MiB per ZIP. ZIP64 is supported; spanned and self-extracting archives are rejected. JSON interpretation is limited to 1 MiB per sidecar; larger raw sidecars remain preserved with a visible issue. Expanded payload limits include unsupported members. TAR framing, padding, and trailers have a separate finite work allowance. These bounds do not guarantee a particular process-memory use.

Metadata matching uses supported exact same-folder names or a unique matching `title`. Ambiguous matches remain unattached. Year collections named `Photos from YYYY` are not treated as user albums. Other source folder names can represent album relationships; naming variations and localized structures may need review. A sidecar with a supported timestamp supplies a separate UTC manifest date. Missing, invalid, conflicting, and ambiguous dates are not inferred from download time.

Malformed ZIP CRC or gzip data, duplicate or case-colliding paths, traversal, backslashes, symbolic links, and nonregular source members are rejected. Trusted local path ancestors are required. ArchiveBridge is not a security sandbox against a hostile process concurrently changing the filesystem.

## Immich 3.3.1

The explicit Immich adapter supports server version 3.3.1 exactly. It requires the seven API-key permissions listed in the [command guide](cli.md), including `asset.download` to verify full remote originals. It does not request `asset.update` or asset-delete permissions. Import scope is the selected local archive. The adapter checks original bytes and album membership, but does not establish whole-account completeness. It uploads original media bytes with a generated minimal date-only XMP sidecar for ready files; raw Takeout JSON sidecars stay local, and their caption or GPS fields are not mapped into Immich. Embedded metadata remains in the unchanged media bytes but is not guaranteed to be interpreted by Immich in a particular way.

Takeout does not include the original filesystem modification time. The generated XMP date and Immich's `fileCreatedAt` and required `fileModifiedAt` use the supported Takeout UTC source date. The adapter waits for Immich's metadata worker and checks those remote dates plus `ExifDateTimeOriginal` before marking the upload ready or beginning album changes. Conflicting dates on an existing asset are refused without metadata changes. A bounded wait or cancellation after upload acceptance preserves the asset ID in the partial report for explicit resume. This does not reconstruct a filesystem timestamp. HTTPS is supported by default; HTTP is limited to an explicit opt-in for literal loopback IP addresses. No remote-delete operation is provided.

ArchiveBridge does not prove Google account completeness, repair damaged files, decrypt encrypted ZIPs, or decode unsupported media. Every published version's verification is limited to the source, package, platform, and checks named in its own release evidence.
